# Защита лабораторной работы №2

## Как объяснить систему

Микросервис — отдельное приложение с определённой ответственностью и собственным API. Auth отвечает за пользователей и токены; Catalog — за книги. Они работают в разных процессах и контейнерах.

Docker запускает приложение вместе с его зависимостями в контейнере. Dockerfile описывает сборку образа. Образ — шаблон, контейнер — запущенный экземпляр. У нас один образ Catalog и два контейнера с разными `INSTANCE_NAME` и `PORT`.

Docker Compose описывает несколько контейнеров, сеть, настройки и проверки здоровья в одном YAML-файле. Команда `docker compose up --build -d` собирает и запускает систему. `depends_on: condition: service_healthy` задерживает запуск Nginx до готовности приложений; дальнейшие отказы обрабатывает уже Nginx.

API Gateway — общий вход в API. Клиент обращается к `localhost:8080`, не зная внутренних адресов сервисов. Nginx направляет `/auth/` в Auth, `/catalog/` — в Catalog. Завершающий `/` у `proxy_pass` позволяет заменить префикс: `/auth/login` превращается в `/login`.

Load Balancing — распределение запросов между экземплярами. Используется round-robin с одинаковыми весами. `instance_id` в ответе показывает, кто обработал запрос. Два Catalog позволяют продолжить чтение каталога при остановке одного процесса.

Service Discovery — хранение и получение сведений о доступных сервисах. Consul содержит имя, адрес, порт и состояние каждого экземпляра. Приложение само регистрируется через HTTP API, Consul опрашивает `/health`. При штатной остановке приложение выполняет дерегистрацию. При недоступности Consul приложение повторяет попытки; после перезапуска Consul регистрации восстанавливаются.

**Отличие:** Nginx обрабатывает пользовательские HTTP-запросы; Consul хранит реестр и проверяет здоровье. В этой работе Nginx использует список upstream из `nginx.conf`, а не API Consul. Docker DNS помогает обновлять IP-адреса при пересоздании контейнеров. Не следует утверждать, что балансировка здесь автоматически настраивается из Consul.

JWT — подписанный токен с данными пользователя и сроком действия. После входа Auth выдаёт токен. Клиент передаёт его в `Authorization: Bearer ...`; `/me` проверяет подпись и срок действия. Подпись защищает от изменения, но **не шифрует** содержимое. Секрет хранится в окружении, файл `.env` не коммитится.

Пароль хранится не открытым текстом: Passlib создаёт PBKDF2-SHA256 с индивидуальной солью и 600 000 итераций. При входе Passlib проверяет введённый пароль против сохранённого хэша. В отличие от прежнего одиночного SHA-256, схема использует соль и многократные вычисления.

## Что происходит при остановке catalog-1

1. Docker отправляет сигнал завершения. Uvicorn выполняет завершающую часть lifespan.
2. Приложение удаляет свою регистрацию из Consul.
3. При неудачном подключении к первому upstream Nginx пробует второй. `max_fails=1` временно исключает отказавший адрес на `fail_timeout=5s`.
4. Запросы GET продолжают возвращать HTTP 200 и `instance_id=catalog-2`.
5. После запуска `catalog-1` регистрируется заново. Когда приложение готово и истёк `fail_timeout`, Nginx снова использует оба экземпляра.

Это отказоустойчивость доступности чтения, а не сохранности данных. Товары в памяти остановленного процесса теряются. Auth и Gateway у нас не дублируются. Автоматический повтор уже отправленных POST не включён, чтобы не создавать дубликаты.

## Сценарий демонстрации

Все команды с телами запросов приведены в README, разделы выполняются по порядку.

1. Показать `git branch` и `git log --oneline`: рабочая ветка, исходный коммит Дмитрия, отдельные инфраструктурные коммиты.
2. Показать Dockerfile и Compose: пять контейнеров, общая сеть, один образ Catalog, разные имена и порты, наружу только 8080 и 8500.
3. Запустить `docker compose up --build -d`, затем `docker compose up -d --wait` и `docker compose ps`. Дождаться пяти `healthy`.
4. Открыть Consul UI `http://localhost:8500/ui/`. Показать три сервиса и HTTP health checks.
5. Открыть `http://localhost:8080/auth/docs`. Зарегистрировать пользователя, войти, показать `/me` с токеном и отказ без токена. Не фотографировать полный JWT.
6. Выполнить раздел CRUD из README с временной остановкой `catalog-2`. Показать POST, список, GET по ID, PUT, DELETE и 404 после удаления. Восстановить второй экземпляр.
7. Выполнить 12 GET `/catalog/products`, показать разные `instance_id`.
8. Остановить `catalog-1`; повторить запросы, показать ответы от `catalog-2`. В Consul первый экземпляр должен исчезнуть.
9. Запустить `catalog-1`, дождаться здоровья и 6 секунд, повторить GET: оба экземпляра снова отвечают.
10. Показать `evidence/integration-results.json` и пояснить: это вывод реальных проверок, время записано в UTC. Полный повтор тестов: `python tests/integration.py`.
11. После демонстрации остановить систему `docker compose down`, если она больше не нужна.

## Возможные вопросы

| Вопрос | Короткий ответ |
|---|---|
| Зачем два Catalog? | Распределять запросы и продолжать работу при отказе одного экземпляра. |
| Почему книга иногда не находится при обоих экземплярах? | У каждого свой словарь в памяти; данные между ними не реплицируются. |
| Как проверяли CRUD? | Через тот же Gateway, временно оставляя один Catalog; затем восстанавливали оба. |
| Почему не добавили общую БД? | Для этой лабораторной используется исходное in-memory хранилище; общая БД не требовалась. |
| Consul балансирует запросы? | Нет, в этой реализации HTTP-запросы балансирует Nginx. |
| Что будет при отказе Consul? | API продолжит работать; регистрация повторяется в фоне и восстановится после запуска Consul. |
| Что будет при принудительном уничтожении процесса? | Lifespan может не выполниться; Consul пометит проверку как critical, затем удалит длительно нездоровую регистрацию. Это отличается от проверенного штатного `docker stop`. |
| JWT зашифрован? | Нет, подписан. Нельзя помещать в него секретные данные. |
| Достаточно ли Docker healthcheck для балансировки? | Нет, в нашей схеме Nginx использует собственные пассивные проверки ошибок upstream. |
| Все API защищены JWT? | Нет, защищён `/me`; Catalog сохраняет исходный открытый CRUD. |
| Это полная высокая доступность? | Нет: дублируется только Catalog, хранилища независимы, Gateway и Auth одиночные. |
| Почему Consul в dev-режиме? | Это локальная учебная демонстрация, без ACL, кластера и постоянного хранения. |

## Скриншоты для отчёта

Текстовые результаты автоматических проверок находятся в `evidence/`. Для скриншотов вручную снять:

1. `docker compose ps` — пять контейнеров, `healthy`, публикация портов.
2. Consul UI — `auth`, `catalog-1`, `catalog-2` и зелёные health checks.
3. Ответ `/auth/me` HTTP 200 с username и ответ без авторизации HTTP 401; скрыть Authorization и JWT.
4. Терминал с последовательностью `catalog-1` / `catalog-2`.
5. `docker stop catalog-1` и последующие успешные ответы `catalog-2`.
6. `docker start catalog-1` и восстановленная последовательность обоих имён.
7. CRUD: создание, изменение, удаление, 404 после удаления.

Не использовать нарисованные скриншоты. Для теоретических источников см. ссылки в README, для конкретной реализации — код и сохранённые результаты тестов.
